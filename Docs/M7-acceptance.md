# M7 应用集成与报警验收

日期：2026-10-13。软件版本 `0.8.0-dev`，基线提交 `0df5c6f`。
本清单提供 T-01～T-12 的实物操作与预期；实际 C 主机模型通过不等于板测通过。
M6 核心上线/telemetry 已有现场证据，全部命令、断网/LWT 和 4 小时稳定性仍待补测，尚无 `v0.7` 发布标签。
M7 的硬件 DoD 完成前不发布 `v0.8`。

## 先确认当前固件能测什么

正常固件：`Docs/M7-app.hex`，测试宏为 0。50 次模型钩子固件：`Docs/M7-test.hex`，仅供 T-12 调试。
只下载 STM32，不升级、擦写 ESP8266；继续使用现有 AT1.7.4.0 / SDK3.0.5。
下载 STM32 时不要擦除外部 W25Q64，也不要清除 RTC 备份域。

**当前 `APP_MQ_DO_ENABLED=0`。两路 MQ 会报告 FAULT，整个报警引擎禁止联动，这是现有接线约束下的预期结果。**
在 MQ 电平和当前 IO1/IO2 接线确认前，可以执行 T-01 的故障路径、T-10 的配置同步、T-11 的持久化/时间和 T-12 模型钩子；
T-02～T-09 的健康布防/气体联动部分不能据此判定通过。

开始健康路径实测前：

1. M8 已按预留接口改为 MQ2 DO→PA12（IO1）、MQ135 DO→PA11（IO2），接线依据 `M8-wiring.md`；历史 M7 镜像仍为 PB0/PB14，不能混用。先测量，不能用软件开关替代电平转换。
2. 两模块用5V供电、AO悬空、DO经转换；保持 TB6612 A 通道永久禁能/PWMA不初始化。未经确认不能直接打开 MQ 宏。
3. 接口问题解决后将 `App/app_config.h` 的 `APP_MQ_DO_ENABLED` 改为 1，再构建、下载正常 M8，并重新记录资源、HEX 哈希；沿用本表的 M7 用例验收应用逻辑。
4. OLED、DHT11、超声波、雷达、Flash、ESP 都应健康。DHT11 为 PB12；超声 TRIG PA15/ECHO PB3；雷达 DO 为 PB4。保持 M5 已验收的舵机/风扇接线。
5. 需要模拟 MQ 高低电平时，先把模块 DO 输出与 MCU 测试输入隔离，再使用已确认的 3.3 V 电平夹具。不能将模块输出直接短接到电源或地；不需要点火或释放烟气。

两路 MQ 和雷达为单 DO 输入，带 `SENSOR_NO_OPEN_WIRE_TEST` 标记。
**这些输入无法仅凭高低电平可靠区分“无人/正常”和“拔线”。全部传感器拔线必报 FAULT 的 DoD 需要硬件开路诊断支持，目前未实现。**
DHT11/超声波的通信超时、FAULT、STALE、数据过期可以检测并禁止联动。

## 观察方式

串口：115200、8N1，保存从启动开始的完整日志。MQTTX 延续 M6 的 Broker 连接。
本设备现场主题前缀为 `smshub/sms-hub-8e7c4b91`；如 KV 中设备名变化，用实际设备名替换。
订阅 `smshub/sms-hub-8e7c4b91/#`。所有下行发布到 `smshub/sms-hub-8e7c4b91/cmd`，QoS 0、**关闭 retained**。

| 主题后缀 | 观察内容 |
| --- | --- |
| `status` | retained `online`，异常掉电 LWT `offline` |
| `telemetry` | 约每 5 秒一次；原字段顺序保持，temp/hum 为 x10，distance 为 cm |
| `config` | retained 的已提交配置：seq、arm、temp(整数℃)、distance(cm)、smoke/air(ms) |
| `event` | `{"type":5,"p":3,"a":0}`：火灾；type6 解除；type7 故障；type8 请求网关时间 |
| `cmd/resp` | 命令回执；配置先 queued，实际 KV 成功后同 id 的 done；失败 rejected |

配置示例：

```json
{"seq":12,"arm":1,"temp":50,"distance":100,"smoke":3000,"air":10000}
```

逐条发送命令，等到最终回执和对应 config 再发下一条。`queued` 不表示已保存。

| payload | 含义 |
| --- | --- |
| `arm=0` / `arm=1` | 写 KV 撤防/布防 |
| `ack=1` | 解除本次报警，保留已提交的布防模式 |
| `th=temp:50` | 温度阈值 0～100℃ |
| `th=distance:100` | 距离阈值 0～500 cm，判断严格小于该值 |
| `th=smoke:3000` | 烟雾确认 0～60000 ms |
| `th=air:10000` | 空气确认 0～60000 ms |
| `fan=45` / `fan=0` | 健康且撤防时的手动控制 |
| `servo=90` / `servo=0` | 健康且撤防时的手动控制 |
| `buzzer=500` | 健康且撤防时蜂鸣 500 ms |
| `time=<Unix秒>` | 接受一个 2020-01-01～2038 上限范围内的 UTC 时间，queued 后由 SensorTask 写 RTC |
| `reboot=1` | 回复 accepted 后复位 |

网络只承载命令和事件，报警计时不依赖网络或 RTC。
`config` 是配置快照；遥测气体值仍是驱动滤波值，引擎使用 DataHub 的原始 DO auxiliary 独立计时，不能用遥测翻转时刻代替原始 DO 起点。

状态日志格式：

```text
报警状态=5 级别=3 故障=0x0 次数=...
配置已保存 序号=... 字段=... 值=...
RTC网关校时 UTC=...
```

| 状态值 | 含义 | 级别值 | 含义 |
| --- | --- | --- | --- |
| 0 | SELF_TEST | 0 | 无报警 |
| 1 | FAULT | 1 | 空气提示 |
| 2 | DISARMED | 2 | 入侵 |
| 3 | WARMUP | 3 | 火灾 |
| 4 | ARMED | | |
| 5 | ALARM | | |

| 故障位 | 项目 | 故障位 | 项目 |
| --- | --- | --- | --- |
| 0x001 | OLED | 0x002 | DHT11 |
| 0x004 | 超声波 | 0x008 | MQ2 |
| 0x010 | MQ135 | 0x020 | 雷达 |
| 0x040 | W25Q JEDEC | 0x080 | ESP AT 未通过 |
| 0x100 | DataHub 快照不可用 | 0x200 | 存储未就绪/停止写入 |
| 0x400 | 执行器请求失败 | | |

故障码按位相加，例如仅 MQ 禁用通常为 `0x018`；若还有故障，以实际组合为准。
OLED 坏掉时无法依靠该屏显示故障，改看串口和 MQTT。

## T-01 上电自检、故障与预热

操作：保存当前 config；上电，观察 OLED、传感器表、Flash JEDEC、ESP AT/网络日志和状态。
若使用当前 MQ 禁用固件，等待 15 秒自检期限。

预期：自检未完成前不联动；期限结束显示 FAULT 和对应位，风扇停、舵机目标 0°、蜂鸣停、黄闪。
当前默认至少有 MQ 的 `0x018`。AT 应答和 Wi-Fi/MQTT 在线是不同检查，路由器离线但 AT 正常不应单独产生 ESP 自检故障。

健康接口准备完成后，发送 `arm=0` 等 done，预期 SELF_TEST→DISARMED。
再发送 `arm=1` 等 done，预期 WARMUP 倒计时约 150 秒→ARMED；预热期间刺激输入不能联动。
已保存为布防模式的重启路径为 SELF_TEST→DISARMED→WARMUP→ARMED，中间 DISARMED 可能只持续一个轮询周期。

记录：逐项日志、故障码照片、预热开始/结束时间、上电执行器状态。

## T-02 单鉴不能触发入侵

前提：全健康、ARMED，distance=100，MQ 原始 DO 正常高。
操作 A：距离稳定大于 120 cm，只在雷达区挥手，确认快照/日志 human=1 并保持至少 5 秒。
操作 B：雷达确认无人 human=0，用静止测试物把距离降至约 30 cm，保持至少 5 秒。

预期：两次都保持 ARMED；没有入侵声光、event5/p2、风扇/舵机动作。
操作 B 应确认雷达实际仍为 0；人靠近摆物导致雷达变 1 不能算作单鉴测试。
记录：human/distance 与状态日志。

## T-03 双鉴、边界与计时中断

操作：保持 human=1，再把稳定距离降至 30～50 cm；从两项健康快照同时成立时计时。
随后解除条件并等待恢复，做一次“成立约 1 秒→移开→重新成立”的中断测试。

预期：同时持续 2 秒才进入 ALARM/入侵；中断后重新计满 2 秒。
紫闪、长鸣、入侵弹窗、event `{"type":5,"p":2,"a":0}` 和日志出现。
从安全基线开始，风扇保持 0、舵机保持 0°；入侵不启动这两项。
恰好 100 cm 不满足 `<100`，99 cm 满足；物理测距有误差，精确等号边界以主机模型为证，板测留出距离裕量。

雷达驱动自带约 1 秒去抖、超声有 5 样本滤波，所以不能要求从挥手瞬间起恰好 2 秒报警。
记录：双项成立时刻、入侵时刻、10 秒解除时刻、event/弹窗。

## T-04 常温烟雾 3 秒与完整火灾联动

前提：ARMED，DHT 温度低于温度阈值；`th=smoke:3000` 已 done。
操作：用隔离电平夹具使 MQ2 原始 DO 低，先试 2 秒后释放，确认不报警；再连续低超过 3 秒。

预期：不足 3 秒不报警；连续 3 秒后 ALARM/火灾，急促蜂鸣、红闪 2 Hz、风扇目标 100%、舵机目标 90°、FIRE 弹窗、
event `{"type":5,"p":3,"a":0}` 和日志请求。风扇约 1 秒缓升，舵机按 50 ms/度约 4.5 秒到 90°。
计时容差包含 MQ 200 ms 采样和 AlarmTask 轮询；用原始 DO auxiliary 的变化作为软件计时起点。
解除低电平后持续 10 秒自动恢复；舵机按原斜率回 0°，风扇停、蜂鸣停。

风扇占用共享 SPI 时，持久日志排队，网络 event 立即入既有 RAM 环；停止后才持久化。不能要求风扇运行时 Flash 同时写。
记录：完整联动视频/日志、DO/灯/蜂鸣波形、风扇和舵机最终位置。

## T-05 高温烟雾 1 秒

操作：在无危险源的环境下，将温度阈值设置为低于当前稳定 DHT 值，例如实际 25℃时设 `th=temp:20`，等 done/config。
先只满足温度条件，保持烟雾正常；然后让 MQ2 原始 DO 连续低。

预期：温度高本身不触发火灾；温度 `>=` 阈值且烟雾低持续 1 秒触发 T-04 同样的火灾动作。
低不足 1 秒不能触发。若烟雾确认配置本来小于 1 秒，高温路径保持更短配置，不延长为 1 秒。
结束后 ack/恢复，重新保存 `th=temp:50`、`th=smoke:3000`。
记录：已提交阈值、DHT 值、DO 起点和报警时刻。

## T-06 空气提示 10 秒

前提：ARMED，无火灾/入侵条件，`th=air:10000` 已 done。
操作：MQ135 原始 DO 先低 9 秒后释放；再低超过 10 秒。

预期：不足 10 秒无提示；连续 10 秒后 ALARM/空气，黄色常亮、风扇目标 45%、AIR NOTICE 弹窗，
event `{"type":5,"p":1,"a":0}` 和日志，无鸣笛。解除条件 10 秒后恢复。
记录：计时、灯色、风扇目标/缓升、蜂鸣引脚保持关闭。

## T-07 优先级、降级与自动恢复

操作：先维持空气提示，再建立双鉴 2 秒，最后建立烟雾 3 秒。
维持低优先级条件，先释放烟雾，再解除双鉴，最后释放空气。

预期：空气→入侵→火灾逐级抢占；火灾期间显示/声光以火灾为准。
烟雾解除不足 10 秒仍为火灾；满 10 秒后降为仍成立的入侵。
双鉴解除 10 秒后降为空气；空气解除 10 秒后回 ARMED。
每次级别变更有对应 event/状态日志。高等级退出时停止它占用的风扇/舵机，防止沿用上一个等级的输出。
清除条件期间重新成立，应重置 10 秒解除计时。
记录：三种成立/解除时间、级别序列和输出。

## T-08 传感器故障禁止联动

操作 A：正常布防时断开 DHT 信号，保持其他条件不变；再恢复接线。操作 B：对超声 ECHO 通信故障做同样测试。
更改接线时先断电；若使用已安装的信号隔离开关可保持供电。分别在无报警和火灾报警中验证质量失效行为。

预期：首次失败造成 STALE 或 FAULT/过期后，下一次报警轮询进入 FAULT，级别清零，风扇停、舵机目标 0°、蜂鸣停、黄闪，
显示 DHT `0x002` 或超声 `0x004`，组合故障按位累加，发送 type7 故障事件。
不沿用旧 GOOD 值触发联动；即使仍有烟雾/双鉴条件，也保持故障安全态。
恢复新鲜 GOOD 数据后经 DISARMED；已保存布防则重新预热 150 秒，撤防则保持 DISARMED。

MQ/雷达拔线只能记录实际表现，**不能把输入正常高或无人当成可检测开路**。
该部分 DoD 标记“硬件诊断前提未满足”，不得填写通过。
OLED 断开时看串口故障位；Flash 故障应停止写入并保留已确认配置，不能为了测试清空 KV。
ESP 本项测试是开机 AT 自检，运行中断网重连沿用 M6。

## T-09 PA0、云端解除与持久撤防

操作：触发一次报警，单击 PA0；再次触发，用 `ack=1`；第三次触发，发送 `arm=0` 并等最终 done。

预期：PA0/ack 解除本次报警并停止联动，仍保留 arm=1；条件未消失时按 1/2/3/10 秒相应确认时间重新报警。
`arm=0` 请求成功入队后优先停止输出、释放 SPI，KV 提交后 config.arm=0、最终 done，持续条件不能再报警。
PA0 在无报警时仍执行原菜单导航；PC13 只关闭弹窗，不清除报警。
FAULT/WARMUP/ARMED/ALARM 中下发 `fan=100`、`servo=90`、`buzzer=500` 应 rejected，不能覆盖状态机输出。
记录：同 id queued→done、ack 回执、状态/执行器变化、KV arm 值。

## T-10 菜单/云端配置闭环与失败边界

操作：发送 `arm=0` 等 done；风扇若为手动运行，先 `fan=0`。通过菜单 Thresholds 把 temp 改为 52 并确认保存。
MQTTX 检查 retained config；再逐条下发 `th=temp:53`、`th=distance:90`、`th=smoke:3500`、`th=air:11000`，每条等 done。
退出编辑后查看菜单；用新阈值复测相应条件，最后恢复 50/100/3000/10000。

预期：只有 KV 成功后 seq 增长、两端显示新值；任务无需重启，条件计时按新配置重新开始。
非法 `th=temp:101`、`th=distance:-1`、`th=air:60001`、`ack=0`、超长 key/value 均 rejected，配置不变。
保存忙时第二个请求可以 rejected，不应声称已经保存；以最终 committed config 为准。

边界：风扇运行期间配置/日志会等待 SPI；不能把长期 queued 当作 done。
若等待中需要撤防，先 `ack=1` 释放报警风扇，再等队列处理；不要连发保存命令填满队列。
火灾条件仍在时可能重新报警，先解除刺激再 ack。
Flash 写失败的停止写入/保留旧值已由实际 C 故障注入模型验证；不要为板测在带电时拔 Flash 或破坏唯一 KV。
记录：菜单照片、config 前后 seq、回执、热加载时间。

## T-11 掉电恢复、仍存在条件与 RTC

操作 A：无联动时保存 temp=52、distance=90、smoke=3000、air=10000、arm=1，逐条等 done 后复位 STM32。
操作 B：保持一个测试报警条件，再复位。最后撤防并恢复默认阈值。

预期：复位后 KV 的模式和阈值保持；执行器先处安全态。
自检通过后重新预热 150 秒，仍成立的报警条件重新计时并报警，不依赖断电前 RAM 状态。
不要把 queued 后立即掉电的未提交值当成必须保存的值。

RTC：日志 `RTC时间来源=1` 表示编译时间(工程时区 UTC+8，转换为 UTC 秒)，2 表示有效备份域，3 表示网关时间，0 表示尚无有效时间。
首次无有效备份才用编译时间，不在每次复位覆盖有效 RTC。保留备份电池的复位应看到来源 2。
没有备份供电时掉电后可能重新使用编译时间；不把过去的编译时间当成实时联网时间。

联网后 event/type8 请求网关校时。当前交付定义了 MQTT 请求/回复入口，未部署常驻网关服务；MQTTX 可人工充当网关。
在电脑 PowerShell 执行：

```powershell
'time=' + [DateTimeOffset]::UtcNow.ToUnixTimeSeconds()
```

立即把输出的完整 payload 发到 cmd，预期 queued、随后日志 `RTC网关校时 UTC=...`，System 页 `RTC source:3`、telemetry.ts 接近电脑 UTC 秒。
queued 仅表示校时入队，实际成功看日志；RTC 写失败保留旧时间。
不回复 type8 时本地状态机和联网均不得阻塞；恢复联网会再请求一次。PC 时间应已校准。
记录：重启前后 config、来源、UTC 与电脑误差、重新报警视频。

## T-12 50 次自动化模型钩子与板上压力观察

先在电脑运行：

```powershell
python .\Docs\test_m7.py
```

预期包含 `PASS T-12 actual firmware hook: 50 mixed alarm/recovery cycles, zero failures`。
该脚本编译实际 alarm_engine/app_time C 实现，检查时长、优先级、故障、回绕、实际 NetTask 配置回执，并非烧录/物理测试。

板上钩子：

1. 断电后将执行器机械负载置于可观察状态；下载 `Docs/M7-test.hex`，Keil 用同次测试构建的 AXF 加载符号。
2. 要重建测试符号，先把 `APP_M7_TEST_ENABLED` 改为 1，执行 `& .\Docs\build.ps1 -Stage M7-test`；不要用正常 AXF 调试测试 HEX。
3. Debug 运行后在 Watch 中观察 `m7_test_request`、`m7_test_cycles`、`m7_test_failures`，将 request 写为 1。
4. 保持 Run。钩子每 AlarmTask 轮询推进一步，使用虚拟时间，约数秒完成；不要长时间 Halt 触发看门狗。
5. 预期 cycles=50、failures=0，日志 `M7循环=50 失败=0`。request=2 可停止；request=1 可重跑。
6. 最后恢复宏 0，执行 `& .\Docs\build.ps1 -Stage M7` 并下载正常固件。

钩子使用独立状态机和本地 scratch 快照，轮换空气/入侵/火灾，不修改 DataHub、不伪造传感器质量、不直接操作执行器；
真实报警引擎仍运行，实际输入成立时仍会联动。它证明状态循环逻辑，不证明机械执行器完成了 50 次动作。
板上实物循环按 T-03/T-04/T-06 触发、T-09 解除，记满 50 次，检查状态序列、故障、堆/各任务栈最低余量及复位次数。
同时检查看门狗故障=0、堆不持续下降；“未测”不能写成“50 次实物通过”。
